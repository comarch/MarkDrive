# Release and rollback

MarkQuire uses Release Please and Semantic Versioning.

## Version sources

- `package.json` is the product version source.
- `package-lock.json` mirrors the package version.
- `.release-please-manifest.json` tracks the last released version.
- `google-workspace-manifest.json` is updated as a Release Please extra file.
- Release notes and `CHANGELOG.md` are generated by Release Please.

Do not edit release versions or generated release notes manually.

## Pre-1.0 policy

Current Release Please configuration applies:

- `fix` and runtime dependency maintenance produce a patch;
- `feat` produces a patch while the project remains pre-1.0;
- a breaking change produces a minor release;
- development dependency, CI, documentation, test, and refactor changes do not
  trigger a product release.

## Automation level

Bootstrap default is checks-only:

- Release Please stays disabled until `ENABLE_RELEASE_PLEASE` is explicitly
  set to `true`.
- Renovate may create dependency pull requests, but all merges stay manual.
- A maintainer reviews and merges the release pull request.
- Release pull request auto-merge stays disabled unless
  `ENABLE_RELEASE_PR_AUTOMERGE` is explicitly set to `true`.
- Major dependency updates remain manual.

## Release flow

1. Configure a release token, test it, then set `ENABLE_RELEASE_PLEASE=true`.
2. Merge validated Conventional Commits to `main`.
3. Release Please creates or updates the release pull request.
4. Review version, changelog, generated files, and CI.
5. Merge the release pull request.
6. Release Please creates the tag and GitHub Release.
7. `publish-release.yml` checks out that tag.
8. CI runs again from the tagged source.
9. The workflow creates `markquire-vX.Y.Z.tar.gz` and a SHA-256 checksum.
10. Both files are attached to the existing GitHub Release.

The release archive contains the static `dist/` application. It is built from
the tag, not from an untrusted pull request.

## Required GitHub configuration

- `RELEASE_PAT`: repository-scoped credential with contents and pull request
  write access for Release Please branches, pull requests, tags, and releases.
- `ENABLE_RELEASE_PLEASE`: set to `true` only after the release token succeeds
  in a manual workflow run.
- `ENABLE_RELEASE_PR_AUTOMERGE`: leave unset or `false` during bootstrap.
- read-only default workflow permissions.
- `contents: write` only in release jobs that need it.
- protected `main` branch and required checks.

See [Repository settings](./REPOSITORY_SETTINGS.md).

## Pre-release verification

```bash
npm ci
npm run validate
npm audit --omit=dev --audit-level=high
npm run promptscript:validate
```

Confirm:

- working tree and staged content are understood;
- generated PromptScript output has no drift;
- release version matches all version sources;
- production artifact is non-empty;
- archive contains no source maps, credentials, local paths, or `.env` files;
- installation documentation matches the artifact.

## Rollback

Prefer a corrective patch over deleting a published release.

1. Disable Release Please auto-merge.
2. Stop the publish workflow when it is still running.
3. Mark a bad release as a pre-release or add a warning to its notes.
4. Revert the smallest faulty source change.
5. Add a regression test.
6. Run the full validation contract.
7. Publish a corrective patch release.
8. Document affected versions and user action.

Do not move or delete a public tag after users may depend on it.

## Disable procedure

- Set `ENABLE_RELEASE_PR_AUTOMERGE` to `false` or remove it.
- Disable the Release Please workflow in GitHub Actions when automation itself
  is unsafe.
- Revoke `RELEASE_PAT` when credential exposure is plausible.
- Keep publishing disabled until required checks and recovery verification pass.
